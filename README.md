# SmartStock — кейс системного и бизнес-аналитика: WMS для малого и среднего бизнеса

## О проекте

Проектирование информационной системы управления складом (WMS) для малого и среднего бизнеса, интернет-магазинов и логистических стартапов. Система закрывает полный цикл складских операций — приём, хранение, отгрузку — и дополняет их аналитикой, визуализацией и элементами ИИ (прогнозирование спроса, голосовой поиск). Технически реализована как SPA на React + REST API на Node.js/Express + PostgreSQL с 3D-визуализацией склада.

> **Репозиторий проекта:** [https://github.com/Kryanrd/SmartStock](https://github.com/Kryanrd/SmartStock)

## Проблема и цель

Малый и средний бизнес не имеет ресурсов для внедрения тяжёлых ERP-систем и продолжает вести складской учёт в Excel или бумажных журналах. Это приводит к типичным проблемам:

- отсутствие структурного представления склада (нет привязки к ячейкам, полкам, зонам);
- ручной ввод и высокая вероятность ошибок;
- отсутствие актуальных остатков в реальном времени;
- сложности с поиском товаров;
- невозможность прогнозировать спрос;
- сложности в обучении новых сотрудников.

**Цель:** спроектировать доступную WMS с низким порогом входа, которая автоматизирует рутинные операции, формализует обработку исключений (брак, несоответствие документов) и даёт владельцу бизнеса прозрачную аналитику.

## Контекст и ограничения

- Учебный проект, выполненный в коменде.
- Стек: React (SPA), Node.js + Express, PostgreSQL, REST API; элементы ИИ (компьютерное зрение, прогнозирование спроса, голосовой поиск).
- Ограничение: минимальный порог входа для пользователей без ИТ-опыта.
- Ограничение по данным: 3D-визуализация и голосовой поиск требуют точной привязки товаров к ячейкам — это предъявляет повышенные требования к модели данных и ограничениям целостности.

## Моя роль

Системный и бизнес-аналитик:

- анализ рынка, целевой аудитории и существующих решений;
- систематизация типичных проблем складского учёта;
- моделирование бизнес-процессов в нотациях IDEF0, ARIS и BPMN;
- формализация исключительных ситуаций (возврат брака, акт о несоответствии);
- проектирование концептуальной модели данных;
- определение функциональных и нефункциональных требований;
- определение метрик эффективности складских операций;
- подготовка матрицы трассировки и критериев приёмки.

## Ключевые аналитические решения

### 1. Анализ рынка и обоснование ниши

В ходе анализа предметной области выявлено, что крупные ERP-решения недоступны малому и среднему бизнесу по стоимости внедрения и сложности сопровождения. Рассмотрены три категории решений — Excel/бумажный учёт, ERP-системы, WMS для SMB — и для каждой зафиксированы ограничения. Это обосновывает нишу SmartStock: **простая, гибкая WMS с низким порогом входа, гибкой иерархией склада и встроенной обработкой исключений**.

Артефакт: [Анализ рынка и целевой аудитории](docs/01-market-and-audience.md).

### 2. Систематизация проблем целевой аудитории

Шесть типичных проблем складского учёта формализованы и связаны с функциями будущей системы. Это позволило не «рисовать экраны», а **обосновывать каждую функцию болью пользователя**.

Артефакт: [Проблемы и цели](docs/02-problems-and-goals.md).

### 3. Моделирование процессов в трёх нотациях

**Почему три нотации:**
- **IDEF0** — верхнеуровневое описание функций и связей (для обсуждения с бизнесом);
- **ARIS (eEPC)** — документопотоки и логика обработки брака (для анализа исключений);
- **BPMN** — детализация с шлюзами и событиями (для передачи в разработку и тестирование).

**Что покрыто моделями:**
- Приём товаров — проверка документов, визуальный осмотр, контроль качества, регистрация в WMS.
- Хранение товаров — определение оптимального места, мониторинг запасов, инвентаризация.
- Отгрузка товаров — комплектация заказов, подготовка транспортных документов, передача перевозчику.

Артефакт: [Моделирование процессов](docs/03-process-modeling.md).

### 4. Обработка исключений 

Особое внимание уделено сценариям, которые часто забывают в требованиях:

- товар пришёл с дефектами → акт о браке → возврат поставщику;
- документы не соответствуют товару → акт о несоответствии → возврат;
- товара нет в наличии при отгрузке → уведомление клиента и перенос заказа.

### 5. Связь ролей и разграничения доступа

Организационная структура (директор, менеджеры по приёмке/хранению/отгрузке, рабочие склада, водители) наложена на процессы. Это основа для матрицы доступа (RBAC) в будущей системе.

### 6. Модель данных и гибкая иерархия склада

Модель данных включает `WAREHOUSES → RACKS → SHELVES → PRODUCTS` и таблицу транзакций. Детализация до ячейки необходима для 3D-визуализации и голосового поиска, но требует продуманных ограничений целостности.

**ER-концепция (основные сущности):**

| Сущность | Назначение |
|---|---|
| `WAREHOUSES` | Склады (название, адрес) |
| `WAREHOUSE_CONFIGS` | Конфигурация размеров: ширина, глубина, высота, число рядов/полок |
| `RACKS` | Ряды (привязка к складу, координаты, размеры) |
| `SHELVES` | Полки (привязка к ряду, уровень, позиция, вместимость) |
| `PRODUCTS` | Товары (SKU, название, габариты, цвет, привязка к полке) |
| `TRANSACTIONS` | История операций: приём (`receipt`), перемещение (`move`), отгрузка (`ship`), инвентаризация (`inventory`) |
| `USERS`, `ROLES` | Пользователи и роли (директор, приёмка, хранение, отгрузка, рабочий, водитель) |

Артефакт: [Модель данных (ERD)](docs/04-data-model.md).

### 7. Требования и критерии приёмки

Сформированы 16 функциональных требований (FR-01…FR-16), 13 нефункциональных (NFR) и 8 бизнес-правил (BR). Для каждого ключевого требования — Gherkin-сценарии, включая исключения (брак, несоответствие, отсутствие товара).

Артефакты: [Требования](docs/05-requirements.md), [Матрица трассировки](docs/06-traceability.md).

### 8. Метрики эффективности

Определены метрики, которые позволяют измерить, работает ли система: точность учёта остатков, время поиска товара, процент ошибок комплектации, оборачиваемость товара, прогнозируемый дефицит/избыток на основе ML-моделей. Каждая метрика привязана к требованиям.

Артефакт: [Метрики](docs/07-metrics.md).

## Технологический стек и архитектура

Техническая часть приведена как подтверждение того, что аналитические решения реализуемы.

| Слой | Технологии |
|---|---|
| **Frontend** | React (SPA), UI-библиотеки, 3D-визуализация склада |
| **Backend** | Node.js, Express |
| **База данных** | PostgreSQL |
| **API** | REST API |
| **ИИ / ML** | Компьютерное зрение, прогнозирование спроса, голосовой поиск |

**Трёхуровневая архитектура:**

```
Frontend (React SPA + 3D + голосовой поиск)
        │ REST API
Backend (Node.js + Express: бизнес-логика, аутентификация, API)
        │ SQL
PostgreSQL (склады, товары, ячейки, транзакции, остатки, история)
```

**Структура репозитория:**

```
SmartStock/
├── backend/
│   ├── migrations/      # Миграции БД
│   ├── server.js        # Точка входа Express
│   └── package.json
├── frontend/
│   ├── public/
│   └── src/             # 3D-визуализация, голосовой поиск, панели, интерфейс поиска
└── .gitignore
```

**Ключевые модули системы:**

| Модуль | Возможности |
|---|---|
| Гибкая структура склада | Зоны, ряды, полки, ячейки; привязка товаров к ячейкам |
| Учёт и перемещение | Приёмка, перемещение, списание, история операций |
| Поиск и фильтрация | По названию, SKU, штрихкоду; по категориям, остаткам, срокам |
| Визуализация склада | 3D-карта, подсветка занятых/пустых ячеек, маршруты |
| Голосовой поиск | Запросы на естественном языке → ячейка на схеме |
| Прогноз и аналитика | Прогноз спроса, рекомендации по пополнению, отчёты |
| Управление складами | Несколько складов с адресами и описаниями |
| Роли и доступ | RBAC для директора, менеджеров и рабочих |
