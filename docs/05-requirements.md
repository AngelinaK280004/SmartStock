# Требования и критерии приёмки — SmartStock

Документ фиксирует требования к WMS SmartStock, выведенные из анализа проблем целевой аудитории, моделей процессов и концептуальной модели данных. Для каждого требования указан источник, связанный процесс, сущность данных и проверяемый критерий приёмки.

## 1. Легенда и соглашения

### 1.1. Типы требований
- **FR** (Functional Requirement) — функциональное требование: что система должна делать.
- **NFR** (Non-Functional Requirement) — нефункциональное требование: как система должна это делать (производительность, безопасность, удобство).
- **BR** (Business Rule) — бизнес-правило, которое система обязана соблюдать.

### 1.2. Приоритеты (MoSCoW)
- **Must** — без этого релиз не имеет смысла.
- **Should** — важно, но можно отложить на следующий релиз при жёстких сроках.
- **Could** — желательно, реализуется при наличии ресурсов.
- **Won't (this release)** — осознанно вне скоупа текущего релиза.

### 1.4. Источники требований
| Код источника | Источник |
|---|---|
| `SRC-PROB` | Типичные проблемы складского учёта (docs/02-problems-and-goals.md) |
| `SRC-PROC` | Модели процессов IDEF0/ARIS/BPMN (docs/03-process-modeling.md) |
| `SRC-ER` | Концептуальная модель данных (docs/04-data-model.md) |
| `SRC-MKT` | Анализ рынка и аудитории (docs/01-market-and-audience.md) |
| `SRC-MET` | Метрики эффективности (docs/07-metrics.md) |

## 2. Роли и матрица доступа 

| Роль | Назначение | Ключевые права |
|---|---|---|
| `director` | Директор склада | Полный доступ, аналитика, управление пользователями |
| `receiving` | Менеджер по приёмке | Приёмка, акты о браке/несоответствии, возврат поставщику |
| `storage` | Менеджер по хранению | Размещение, перемещение, инвентаризация |
| `shipping` | Менеджер по отгрузке | Комплектация, отгрузочные документы, работа с клиентом |
| `worker` | Рабочий склада | Только операции перемещения/комплектации, без редактирования документов |
| `driver` | Водитель | Просмотр назначенных доставок, отметка о передаче |

**Правило RBAC (BR-01):** любое действие, изменяющее документы или остатки, доступно только ролям `director`, `receiving`, `storage`, `shipping` в пределах их зоны ответственности. Роль `worker` не может редактировать документы.

### 3.2. Детализация ключевых FR

**FR-01. Настройка структуры склада**
- Система позволяет создать склад и задать его конфигурацию: количество рядов, полок на ряд, размеры ячеек.
- Конфигурация хранится в `WAREHOUSE_CONFIGS` и связана со складом.
- Изменение конфигурации после размещения товаров требует явного подтверждения и не должно приводить к потере данных о товарах. `[УТОЧНИТЬ: поведение при уменьшении числа полок, если на них уже есть товар]`

**FR-02. Приёмка товара**
- На входе — уведомление о поступлении и документы (ТТН, сертификаты, спецификации).
- Система проводит пользователя через шаги: проверка документов → визуальный осмотр → регистрация.
- Результат шага фиксируется в `TRANSACTIONS` с типом `receipt` (при успехе) или создаётся акт (FR-03/FR-04) при исключении.

**FR-03. Акт о браке**
- При обнаружении дефекта система создаёт запись о браке, меняет статус товара на «возврат поставщику» и **не размещает** товар на складе.
- Акт должен содержать: номер, дату, поставщика, перечень дефектов, ФИО ответственного (по роли `receiving`), ссылку на ТТН.

**FR-04. Акт о несоответствии документов**
- При расхождении товара и документов система создаёт акт о несоответствии и инициирует возврат.
- Акт должен содержать: номер, дату, поставщика, суть несоответствия (что именно не совпало), ссылку на документы.

**FR-05. Размещение с контролем вместимости**
- Перед размещением система проверяет `SHELVES.capacity` и текущую занятость ячейки.
- Если вместимости не хватает — предлагает альтернативные ячейки или блокирует операцию с понятным сообщением.

**FR-07. Актуальные остатки**
- Остаток `PRODUCTS.quantity` обновляется атомарно при каждой операции (приёмка, перемещение, отгрузка, инвентаризация).
- Остаток не может стать отрицательным (см. BR-02).

**FR-09. Поиск**
- Поддерживается поиск по `PRODUCTS.name`, `PRODUCTS.sku`, а также по штрихкоду.
- Поиск возвращает товар и его местоположение (склад → ряд → полка → ячейка).

**FR-11. Голосовой поиск**
- Пользователь формулирует запрос на естественном языке (например, «где лежит товар X с характеристикой Y»).
- Система распознаёт сущность товара, находит его ячейку и подсвечивает её на схеме склада.
- Fallback: если товар не распознан — предложить обычный поиск (FR-09).

**FR-13/FR-14. Отгрузка**
- При получении заказа система проверяет наличие товара.
- Если товара достаточно — резервирует его, проводит комплектацию, формирует отгрузочные документы.
- Если товара недостаточно — уведомляет менеджера, предлагает перенос или отмену заказа.

**FR-16. RBAC**
- Проверка роли выполняется на уровне API до выполнения операции.
- Матрица прав строится на основе `ROLES.code` и зоны ответственности (см. раздел 2).

## 4. Нефункциональные требования (NFR)

| ID | Требование | Метрика / критерий | Метод проверки |
|---|---|---|---|
| NFR-PERF-01 | Время поиска товара | p95 ≤ 2 с при номенклатуре до 10 000 SKU | Нагрузочный тест |
| NFR-PERF-02 | Время отклика голосового поиска | p95 ≤ 3 с  | Замер на тестовом наборе запросов |
| NFR-PERF-03 | Время обновления остатка после операции | ≤ 1 с | Интеграционный тест |
| NFR-USA-01 | Понятность интерфейса для нового сотрудника | Пользователь выполняет приёмку с первой попытки без обучения  |
| NFR-USA-02 | Понятность визуализации склада | Пользователь находит товар по визуальной схеме не дольше, чем через поиск | Сравнительный замер |
| NFR-DATA-01 | Неотрицательность остатков | CHECK в БД | Миграция + тест |
| NFR-DATA-02 | Уникальность SKU | UNIQUE-индекс | Миграция + тест |
| NFR-DATA-03 | Атомарность операций с остатками | Операция выполняется в транзакции | Интеграционный тест |
| NFR-SEC-01 | Разграничение ролей на уровне API | Запрос от роли без прав → 403 | Тест-кейс по матрице RBAC |
| NFR-SEC-02 | Пароли хранятся как хеши | Проверка БД | Code review |
| NFR-SEC-03 | Аудит изменений документов | Для каждого акта — запись в `TRANSACTIONS` с `user_id` | Проверка логов |
| NFR-OBS-01 | Логирование ошибок операций | Ошибки с контекстом (кто, что, когда) | Проверка логов |
| NFR-COMPAT-01 | Поддержка современных браузеров | Chrome, Firefox, Edge, Safari (последние 2 версии) | Ручное тестирование |

## 5. Бизнес-правила (BR)

| ID | Правило | Обоснование | Где соблюдается |
|---|---|---|---|
| BR-01 | Действия с документами и остатками доступны только авторизованным ролям в пределах зоны ответственности | Защита от ошибок и злоупотреблений | API (FR-16) |
| BR-02 | `PRODUCTS.quantity >= 0` | Не допускать отрицательных остатков | CHECK в БД (NFR-DATA-01) |
| BR-03 | `PRODUCTS.sku` уникален | Идентификация товара | UNIQUE-индекс (NFR-DATA-02) |
| BR-04 | Товар с дефектом или несоответствием документов не размещается на складе | Логика ARIS/BPMN | FR-03, FR-04 |
| BR-05 | Размещение не превышает `SHELVES.capacity` | Целостность визуализации и учёта | FR-05 |
| BR-06 | Каждая операция с остатком фиксируется в `TRANSACTIONS` | Аудит и аналитика | NFR-SEC-03 |
| BR-07 | Отгрузка возможна только при достаточном остатке | Логика BPMN «Отгрузка» | FR-13, FR-14 |
| BR-08 | Инвентаризация создаёт корректирующие транзакции, а не перезапись остатка «напрямую» | Сохранение истории | FR-08 |

## 6. Критерии приёмки (Gherkin)

Каждый блок — самостоятельный Feature. Формулировки ссылаются на сущности из `docs/04-data-model.md`. Пометки `[СОЗДАТЬ ПОЛЕ]` означают, что сценарий требует расширения модели данных (см. открытые вопросы Q1, Q7, Q9–Q11 в разделе 7).

### 6.1. FR-01: Настройка структуры склада

```gherkin
Feature: Настройка структуры склада
  Scenario: Создание склада с рядами и полками
    Given пользователь с ролью "director"
    When он создаёт склад с 10 рядами и 5 полками в каждом
    Then в системе появляются 10 рядов и 50 полок
    And каждая полка имеет уникальный код в рамках склада

  Scenario: Попытка изменить конфигурацию при наличии товаров
    Given на складе есть размещённые товары
    When пользователь уменьшает число полок
    Then система запрашивает подтверждение
    And при отказе изменения не применяются
```

### 6.2. FR-02: Успешная приёмка (позитивный сценарий)

```gherkin
Feature: Приёмка товара без брака
  Scenario: Приёмка качественного товара с полным пакетом документов
    Given поставщик привёз товар и есть ТТН, сертификат, спецификация
    And пользователь с ролью "receiving" начал приёмку
    When он подтверждает, что документы соответствуют и дефектов нет
    Then товар регистрируется в системе
    And в TRANSACTIONS создаётся запись с типом "receipt"
    And товар доступен для размещения (FR-05)
```

### 6.3. FR-03: Приёмка с браком

```gherkin
Feature: Приёмка товара с дефектом
  Scenario: Обнаружен брак при визуальном осмотре
    Given поставщик привёз товар и есть ТТН
    And пользователь с ролью "receiving" начал приёмку
    When он фиксирует дефект
    Then система создаёт "Акт о браке" [СОЗДАТЬ ПОЛЕ: сущность ACT или поле в TRANSACTIONS]
    And товар помечается как "возврат поставщику" [СОЗДАТЬ ПОЛЕ: PRODUCTS.status или TRANSACTIONS.outcome]
    And товар не размещается на складе
    And событие фиксируется в TRANSACTIONS
```

### 6.4. FR-04: Несоответствие документов

```gherkin
Feature: Проверка документов при приёмке
  Scenario: Отсутствует сертификат качества
    Given товар прошёл визуальный осмотр
    When менеджер по приёмке сверяет документы
    And сертификат качества отсутствует
    Then система создаёт "Акт о несоответствии" [СОЗДАТЬ ПОЛЕ: сущность ACT]
    And инициирует возврат поставщику
    And товар не размещается на складе
```

### 6.5. FR-05: Размещение с контролем вместимости

```gherkin
Feature: Размещение товара
  Scenario: Вместимость полки исчерпана
    Given полка имеет capacity = 100 единиц (шт)
    And на полке уже размещено 100 единиц
    When пользователь пытается разместить ещё 10 единиц
    Then система блокирует операцию
    And предлагает альтернативные полки

  Scenario: Вместимость полки достаточна
    Given полка имеет capacity = 100 единиц
    And на полке размещено 50 единиц
    When пользователь размещает ещё 30 единиц
    Then операция выполняется успешно
    And остаток на полке — 80 единиц
```

### 6.6. FR-06: Перемещение

```gherkin
Feature: Перемещение товара
  Scenario: Перемещение между полками
    Given товар находится на полке A в количестве 20 единиц
    When пользователь перемещает 5 единиц на полку B
    Then на полке A — 15 единиц, на полке B — 5 единиц
    And в TRANSACTIONS создана запись с типом "move"
```

### 6.7. FR-07: Актуальные остатки

```gherkin
Feature: Остатки
  Scenario: Остаток обновляется после отгрузки
    Given на складе 100 единиц товара
    When менеджер отгружает 30 единиц
    Then остаток в системе — 70 единиц
    And изменение отражено в течение NFR-PERF-03 (≤ 1 с)
```

### 6.8. FR-08: Инвентаризация

```gherkin
Feature: Инвентаризация
  Scenario: Расхождение по итогам инвентаризации
    Given системный остаток товара — 50 единиц
    When по итогам инвентаризации фактически обнаружено 47 единиц
    Then система создаёт корректирующую транзакцию типа "inventory"
    And новый остаток — 47 единиц
    And сохраняется причина расхождения [СОЗДАТЬ ПОЛЕ: TRANSACTIONS.reason или сущность INVENTORY_ADJUSTMENT]
```

### 6.9. FR-09: Поиск

```gherkin
Feature: Поиск товара
  Scenario: Поиск по SKU
    Given в системе есть товар с SKU "SKU-001"
    When пользователь вводит "SKU-001"
    Then в выдаче товар и его местоположение (склад → ряд → полка → ячейка)

  Scenario: Поиск по названию
    Given в системе есть товар "Молоко 1л"
    When пользователь вводит "молоко"
    Then в выдаче товар "Молоко 1л" и его местоположение

  Scenario: Поиск по штрихкоду
    Given у товара есть штрихкод [СОЗДАТЬ ПОЛЕ: PRODUCTS.barcode]
    When пользователь сканирует штрихкод
    Then в выдаче товар и его местоположение
```

### 6.10. FR-10: Визуализация склада

```gherkin
Feature: Визуализация склада
  Scenario: Подсветка занятых ячеек
    Given в системе есть склад с 10 рядами и 5 полками
    And на некоторых полках размещены товары
    When пользователь открывает схему склада
    Then занятые ячейки подсвечены цветом
    And при выборе ячейки видны товары в ней

  Scenario: Поиск через визуализацию
    Given пользователь ввёл SKU в поиск
    When система нашла товар
    Then ячейка товара подсвечена на схеме
    And время поиска не превышает показателя обычного поиска (NFR-USA-02)
```

### 6.11. FR-11: Голосовой поиск

```gherkin
Feature: Голосовой поиск
  Scenario: Запрос на естественном языке
    Given пользователь произносит "где лежит товар X с характеристикой Y"
    When система распознаёт товар
    Then отображается ячейка товара на схеме склада
    And время ответа ≤ целевого значения (NFR-PERF-02)

  Scenario: Товар не распознан
    Given запрос не удалось сопоставить с товаром
    When система не находит совпадений
    Then предлагается обычный поиск (FR-09)
    And пользователь получает понятное сообщение об ошибке
```

### 6.12. FR-12: Прогноз спроса

```gherkin
Feature: Прогнозирование спроса
  Scenario: Рекомендация по пополнению
    Given по товару накоплена история транзакций за период ≥ N месяцев [УТОЧНИТЬ: минимальный объём]
    When система рассчитывает прогноз
    Then отображается рекомендация: "пополнить X единиц к дате Y"
    And рекомендация сопровождается факторами, повлиявшими на прогноз

  Scenario: Недостаточно данных для прогноза
    Given по товару нет достаточной истории
    When система не может построить прогноз
    Then пользователь получает сообщение о недостатке данных
    And рекомендация не формируется
```

### 6.13. FR-13, FR-14: Отгрузка

```gherkin
Feature: Отгрузка товара
  Scenario: Успешная отгрузка
    Given поступил заказ на 30 единиц товара
    And на складе 100 единиц
    When менеджер запускает комплектацию
```
